## 저장·안전 계약

최상위 저장 키를 늘리지 않는다. `notes[]`의 `teamTask` 하위 객체에 업무 본문을 보관한다. 일반 `text`는 고정 `[팀 업무]` 표시이며 개인 할 일, 음성 메모, `aiListNotes` 조회와 분리한다. 담당자 필터는 개인정보 보호 기능이 아니다.

팀 업무 변경 전 강제 로컬 안전판을 만든다. 공통 `guardedPersistCurrentState`에 후보 notes와 현재 자료 확인 함수를 전달하며, 낮은 수준의 원자 쓰기 진입점을 추가하지 않는다. 기기 원자 저장이 끝나기 전에는 후보를 live state에 넣지 않아 기존 클라우드/백업 예약에 미확정 내용이 노출되지 않는다. 원자 쓰기 직전에도 현재 자료와 비교하며, 다른 탭/현장/업무 변경·중복 ID·기기 저장 실패 시 입력을 남기고 중단한다. 커밋 직후 변경 경합을 발견하면 최신 화면을 덮어쓰지 않고 재확인을 요구한다.

개인 완료 일괄 삭제·단건 삭제와 회의록 삭제가 같은 ID의 팀 업무를 지우지 않도록 격리했다. 현장·사진 없이 업무만 있는 신규 기기도 스냅샷·불러오기 보호·JSON 내보내기를 지원하고 안전판 화면에 메모/업무 수를 표시한다. 안전판은 최근 12개 시점의 이 브라우저 보관이며 서버 백업/영구 변경 이력과 다르다.

실제 `_현장.json`, 사진, 장부, 연락처, 계정, 서버 설정, 자동 발송은 건드리지 않았다. 가상 데이터와 외부 요청을 차단한 독립 브라우저만 사용한다.

## 5인 실운영에 아직 필요한 단계

| 우선순위 | 기능 | 이번 상태 / 필요한 확인 |
| --- | --- | --- |
| 1 | 담당자·기한·인수인계·현장별 진행 확인 | 이번 로컬 구현 |
| 2 | 직원별 로그인, 퇴사자 접근 차단, 관리자/직원 권한 | PWA에는 미구현. 별도 관리사무소 포털 인증을 업무판 권한으로 간주하면 안 됨. 계정·서버 설계 및 승인 필요 |
| 3 | 다섯 기기 동시 편집, 업무별 충돌 검증·변경 이력 | 현재 전체 JSON 교체 구조. 업무별 서버 revision/원자 변경 API 및 사용자 인증을 먼저 설계해야 함 |
| 4 | 지정 직원 알림·열람·확인 요청 승인 | 미구현. 알림 채널·발송 동의·실패 재시도 정책 필요. 이번에 실제 알림을 보내지 않음 |
| 5 | 직원별 일일 마감·공수/자재 연결 | 기존 일정·작업일지·인건비 기능에 명시적 직원 ID 연결부터 검토. 기존 숫자/이름만으로 직원을 추정하지 않음 |

임시로 공동 자료를 운영할 때는 다섯 기기를 모두 최신 버전으로 맞추고 저장 경로를 하나로 통일한다. 한 사람이 저장을 마친 후 다음 사람이 최신 자료를 불러와 편집한다. 직접 Drive 저장과 중계 저장을 섞는 것은 충돌 감지 누락 위험이 있다. Google 비밀번호나 공용 키를 직원에게 공유하라는 안내가 아니다. 독립 계정 5개로 로그인하면 자동으로 같은 회사 자료에 연결되는 구조도 아니다.
