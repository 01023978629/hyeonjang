# 마스터 비밀번호 확장 — 서버 검증·인계

2026-09-08. 실제 계정이나 운영 비밀번호를 변경하지 않은 로컬 후보다.

## 범위

- 기존 직원과 기존 마스터의 숫자 6자리 로그인 유지.
- 서버가 확인한 `system_admin`에만 공백 없는 8~64자 ASCII `!`~`~` 비밀번호 추가.
- 원문 문자열 그대로 처리. 공백 제거·대소문자 변환·숫자 자동변환 없음.
- 로그인 실패 잠금, 세션 무효화, 단지 격리, 역할 ceiling, 마지막 관리자 보호 유지.
- 마스터를 직원으로 바꿀 때 새 6자리 비밀번호 필수. 입력 거부 시 새 계정/단지를 만들지 않음.
- 기존 `loginCode` API, 해시·소금값·pepper, Sheets 헤더, PWA·사진 중계는 유지.
- `portalHealth.authPolicy`는 새 서버에서 `master-password-v1`이다. 계정 존재나 인증 성공을 뜻하지 않는다.

## 검증

실제 계정 대신 독립 VM의 가짜 입력과 가짜 Sheets만 사용한다.
최종 전체 회귀 127/127 통과(12.8분, 동시 2, 0 실패, 재시도 없음, 종료코드 0).
교차 입력 검사 스크립트: 작업공간 `tmp/master-password-20260908/credential-parity.cjs`.

- 교차 입력 규약 828/828 통과: 원문·길이 경계·공백/제어문자·형변환 거부·역할별 형식.
- 독립 리뷰에서 비밀번호-only 변경의 저장 실패 재시도 성공 오보고를 발견해 수정했다.
  현재 권한을 먼저 검사하고, 저장된 대상의 역할·소금값 기반 해시까지 일치해야
  이미 처리된 비밀번호 요청으로 판단한다.
- 별도 VM에서 `Users` 저장 직전/직후 실패를 주입하고 재시도 후 새 비밀번호 로그인,
  세션 버전 총 1회 증가, 저장 직후 재시도 시 해시/소금값 재발급 없음 확인.
- 실제 비밀번호 원문·계정 정보는 테스트나 로그에 입력하지 않았다.
- 서버 단위검사 2파일 통과. 원문/현재 역할/강등/저장 재시도 보호를 제거한 변이 4종 모두
  실제 조건 변경을 확인한 뒤 종료코드 1로 검출했다.

## 배포·계정 발급 순서

운영 상태 읽기 확인(2026-09-08): 기존 포털 `/exec`는 `ok:true`, `service:office-portal-v3`,
`enabled:true`, `authPolicy` 미제공이다. 새 비밀번호 규칙은 아직 운영에 적용되지 않았다.
소유자 Google 프로젝트 편집 화면 접근은 확인했지만, 실행·속성 수정·비밀번호 입력은 하지 않았다.

1. 서버/프런트 소스의 최종 검사와 승인된 파일 목록 확인.
2. 승인 후 기존 독립 포털 Apps Script의 소스만 갱신하여 배포. 기존 버전과 설정 보존.
3. 실제 `/exec`의 `authPolicy` 확인. PWA/Drive relay 서버 URL·속성은 변경하지 않음.
4. 승인 후 만물 로그인/관리 화면을 GitHub Pages로 배포하고 공개 자산 확인.
5. 소유자가 기존 마스터 존재 여부를 확인. 기존 계정이 있으면 임의 초기화하지 않음.
6. 마스터는 아파트 직원 계정이 아닌 계정·권한 관리 역할이다. 설정 시 실제 사용자 비밀번호를
   코드나 문서에 넣지 않고 사장님이 비밀번호 입력·확정 단계를 직접 수행한다.
7. 실제 로그인과 관리 메뉴를 확인한 뒤에만 계정 발급 완료로 보고.

긴 비밀번호 발급 후 6자리 전용 구버전으로 단순 롤백하면 로그인이 불가능하다.
소유자 인증에 의한 승인된 복구를 먼저 준비한다. 계정 생성과 기존 비밀번호 초기화는 별도 작업이다.
