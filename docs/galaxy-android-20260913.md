# 현장 갤럭시 연결앱 — 설치·검증 안내

작성일: 2026-09-13

## 요약과 현재 상태

갤럭시 1대에서 기존 현장 웹을 열어 사용하는 Android 연결앱을 준비한다. 아이폰 앱은 이번 범위에서 제외한다. Mac은 필요하지 않으며 Windows에서 Android 빌드를 진행한다.

이번 버전은 기존 웹을 별도 WebView에 복제하는 앱이 아니다. 지원 브라우저의 Trusted Web Activity(TWA) / Custom Tabs로 운영 현장 웹을 연다. 네이티브 사진 앱이나 새 동기화 서버를 추가하는 작업과는 구분한다.

| 항목 | 계획 / 확인 상태 |
|---|---|
| 연결 대상 | `https://01023978629.github.io/hyeonjang/` 고정 |
| APK 버전 | `1.0.0` / versionCode `1`, 패키지 `kr.manmool.hyeonjang` |
| 지원 기준 | APK minSdk `24`(Android 7.0), targetSdk `36` 확인. 지원 브라우저는 별도 필요 |
| APK 생성·서명 검사 | 로컬 release 빌드·v2/v3 서명·정렬 검사 통과, 디버그 불가 |

| 도메인 연결 검증 | 루트 `assetlinks.json` 미배포, 전체 화면 검증 미완료 |

APK 생성이나 에뮬레이터 실행이 성공해도 실제 갤럭시의 촬영·Drive 업로드·기존 자료 확인을 완료한 것으로 기록하지 않는다. 아래 상태는 담당자가 최종 증거를 확인한 뒤 갱신한다.

## 기존 자료가 보이는 조건

화면과 웹 저장소는 연결앱을 실행하는 브라우저가 관리한다. 연결앱 자체가 브라우저의 쿠키·로그인 토큰·IndexedDB를 읽어 복제하는 구조는 아니다. [Android TWA 개요](https://developer.android.com/develop/ui/views/layout/webapps/trusted-web-activities)

- 같은 휴대폰의 같은 브라우저·프로필·사이트에서 기존 자료를 사용하는 것이 기본 전제다.
- Chrome에 있던 자료가 Samsung Internet으로, Samsung Internet에 있던 자료가 Chrome으로 자동 이동하지 않는다. 시크릿 모드·다른 프로필·업무 프로필도 동일 자료라고 가정하지 않는다.
- 기본 브라우저를 바꾸거나 브라우저 데이터를 지우면 로그인과 현장 목록이 달라질 수 있다. 앱을 추가한다고 브라우저 자료를 지우거나 새 자료로 덮지 않는다.
- 기존 사진의 미리보기 표시와 원본의 서버 백업 완료는 별개다. 앱의 백업·사진 보관 상태와 실제 서버 결과를 구분해서 확인한다.
- PC와 갤럭시가 같은 계정으로 로그인했다는 사실만으로 현장 자료 전체가 자동 동기화된다고 판단하지 않는다. 기존 Drive/중계 연결과 저장·불러오기 결과를 확인한다.
- 처음 열었을 때 자료가 비어 보이면 신규 현장을 만들거나 빈 자료를 서버에 저장하지 말고, 먼저 기존에 사용한 브라우저·프로필을 확인한다.

## 첫 설치 순서

1. 기존에 사용하던 브라우저에서 현장 웹을 열어 현장 목록이 정상인지 확인한다. 백업 기능의 성공 시각·결과를 확인하고 기존 브라우저와 원본 사진은 유지한다.
2. 갤럭시의 Android 버전과 설치된 브라우저를 확인한다. 브라우저는 신뢰할 수 있는 공식 앱 스토어에서 업데이트한다. Android 최소 버전이 맞더라도 브라우저 지원 여부는 별도 확인한다.
3. 개발자가 최종 검사 후 전달한 APK만 받는다. 전달 경로, 파일명, 버전과 함께 제공되는 SHA-256 값을 비교한다. 파일명만 같다는 이유로 같은 APK라고 판단하지 않는다.
4. 설치 화면에 표시되는 앱 정보와 출처를 확인한다. 설치 출처 허용이 필요한 경우 **이번 APK를 직접 연 출처만** 허용하고 설치가 끝나면 허용을 다시 끈다. 메뉴명은 Android/One UI 버전에 따라 다를 수 있다. [Samsung 설치 출처 안내](https://www.samsung.com/us/support/troubleshoot/TSG10001913/)
5. Auto Blocker, Play Protect, 회사 보안 정책이 설치를 차단하면 전역 보안을 끄거나 차단을 우회하지 않는다. 설치를 멈추고 기존 현장 웹으로 사용한다. 스토어 배포 등 다른 경로가 필요한지 별도로 검토한다. [Samsung Auto Blocker 안내](https://www.samsung.com/nz/support/mobile-devices/protect-your-galaxy-device-with-the-new-auto-blocker-feature/)
6. 아이콘을 눌러 처음 실행하고 아래 실기기 점검을 진행한다. 브라우저 또는 Google에서 권한을 요청하면 대상 사이트·계정·요청 권한을 확인한 뒤 필요한 작업에 한해 사용자가 승인한다.

이 문서에는 아직 공개 APK 다운로드 링크가 없다. 검증되지 않은 외부 APK를 대신 받지 않는다.

## 주소줄이 보일 수 있는 이유

전체 화면 TWA는 앱 서명과 사이트의 소유 연결 검증이 필요하다. 검증이 없거나 실패하면 브라우저 주소줄이 있는 Custom Tab으로 열릴 수 있다. 이는 검증을 우회해서 숨길 항목이 아니다. [Android TWA 시작 안내](https://developer.android.com/develop/ui/views/layout/webapps/guide-trusted-web-activities-version2)

이 사이트의 연결 검증 파일은 다음 **도메인 루트 경로**에서 제공되어야 한다.

`https://01023978629.github.io/.well-known/assetlinks.json`

`/hyeonjang/.well-known/assetlinks.json`에만 파일을 넣는 것으로 루트 검증을 대신할 수 없다. 현재 루트 파일은 미배포 상태다. 후속 작업에는 도메인 루트 배포 권한 확인, 최종 APK의 패키지명·공개 인증서 지문 대조, 루트 변경 승인, 공개 응답 확인이 필요하다. 서명 키·비밀번호를 검증 파일에 넣지 않는다.

주소줄이 보이는 첫 버전도 설치해 사용할 수 있는지는 실기기에서 확인해야 한다. 지원 브라우저가 없거나 보안 경고가 나타나면 이를 무시하지 않고 기존 브라우저에서 운영 주소를 직접 확인한다.

## 업데이트 원칙

웹 화면과 APK는 업데이트 경로가 다르다.

- **웹 기능:** 승인된 현장 웹 배포와 기존 서비스워커 업데이트 절차를 따른다. APK를 새로 설치했다고 미배포 웹 기능이 생기는 것은 아니다.
- **APK 연결 기능:** 같은 패키지명과 같은 서명 키로 만든 새 버전을 기존 앱 위에 설치한다. 업데이트 문제를 해결하려고 먼저 앱을 삭제하거나 브라우저 데이터를 초기화하지 않는다. 서명이 다르다는 오류가 나면 설치를 멈추고 제작자에게 확인한다. [Android 앱 서명 안내](https://developer.android.com/studio/publish/app-signing)
- 업데이트 전에 업로드·저장이 진행 중인지 확인하고 완료 또는 실패 상태를 기록한다. 열려 있는 업무 화면에서 강제로 업데이트하지 않는다.
- 설치 후 현장 목록, 웹 버전, 브라우저, Drive 연결 상태를 다시 확인한다. 다른 브라우저로 연결된 경우 이전 브라우저를 유지한 채 원인을 확인한다.
- 첫 버전에는 APK 자동 업데이트를 보장하지 않는다. 검증된 다음 APK를 별도로 전달받는 방식이다.

서명 키와 비밀번호는 저장소 밖의 비공개 위치에서 보관한다. 키를 잃으면 같은 서명으로 후속 APK를 만들 수 없으므로 별도 안전 백업이 필요하다. 키·비밀번호·개인 토큰을 Git 저장소, APK 전달 폴더, 공개 문서 또는 작업 로그에 넣지 않는다.

## 갤럭시 실기기 확인 — 6개 항목

먼저 개인정보가 없는 작은 시험 사진을 사용한다. 실제 Drive에 파일을 추가하는 시험은 사용자 동의와 대상 폴더 확인 후 진행한다. 기존 프로젝트·사진을 삭제하거나 덮어쓰는 시험은 하지 않는다.

| 번호 | 시험 | 통과 기준 | 결과 |
|---|---|---|---|
| 1 | 첫 실행·기존 자료 | 실행 브라우저/프로필을 확인하고 기존 웹의 현장 목록과 대조한다. 잘못된 사이트 이동이나 빈 자료 덮어쓰기가 없다. 주소줄 표시 여부를 기록한다. | 확인 전 |
| 2 | 갤러리 사진 선택 | 작은 시험 사진을 선택해 현장·작업명을 확인한다. 취소하면 추가되지 않고, 저장 후 중복 없이 다시 조회된다. 미리보기와 원본 백업 상태를 각각 확인한다. | 확인 전 |
| 3 | 카메라·동영상 선택 | 실제 갤럭시의 브라우저 촬영/선택 창을 확인한다. 촬영 취소 후 화면이 정상이며, 지원되는 입력만 처리한다. 동영상이 거절되거나 서버 원본 전송을 지원하지 않으면 제한으로 기록하고 업로드 성공으로 표시하지 않는다. | 확인 전 |
| 4 | Google Drive 연결·결과 | 사용자가 직접 계정·권한을 확인한다. 승인된 시험 폴더에서 저장 결과와 파일을 대조한다. 인증 취소·만료·실패가 성공으로 오표시되지 않는다. | 확인 전 |
| 5 | 통신 단절·닫았다 열기 | 시험 자료로 통신을 끊었다 복구하고 화면을 닫았다 다시 연다. 저장/전송 대기/실패를 구분한다. 원본이 남지 않는 경로는 제한으로 기록하며 자동 재전송을 가정하지 않는다. | 확인 전 |
| 6 | 같은 서명 업데이트·다운로드 | 같은 서명의 다음 시험 APK를 덮어설치하고 기존 자료·브라우저 연결을 재확인한다. 개인정보 없는 작업일지 파일을 내려받아 실제 파일 열기까지 확인한다. | 확인 전 |

시험 기록에는 갤럭시 모델, Android/One UI 버전, 브라우저 종류·버전, APK 버전·해시, 확인 시각과 각 결과를 남긴다. 고객 개인정보, 토큰, 계정 비밀번호는 기록하지 않는다. 설치 파일 하나만 생성된 단계에서는 6번의 업데이트 검증도 완료가 아니다.

## 이번 버전에 포함하지 않는 기능

- 네이티브 카메라·갤러리 엔진: 기존 웹/브라우저의 사진 선택 기능을 사용한다.
- 앱을 닫거나 화면을 꺼도 계속되는 원본 사진·동영상 백그라운드 업로드 보장.
- 원본 사진·동영상의 새 영구 보관소, 다른 브라우저 자료의 자동 복사.
- 모든 동영상 형식·HEIC 파일의 변환 및 서버 전송 보장.
- 기기 간 자동 동기화 완료 보장, 여러 직원의 동시 수정 충돌 해결.
- 직원 로그인·관리자 권한을 새로 부여하는 기능. 앱을 설치하는 것과 업무 접근 권한은 별개다.
- 새 푸시 알림, 자동 문자/고객 발송, 새 서버·계정·Apps Script 설정.
- 아이폰 IPA 제작, TestFlight, Apple 개발자 가입.

## 개발자 재현 방법

저장소의 `android-galaxy/`에서 JDK 17, Android SDK platform 36 및 build-tools 36.0.0을 사용한다.
Gradle wrapper는 8.13으로 고정하며 배포 ZIP 및 wrapper JAR의 공식 SHA-256을 확인했다.

```powershell
.\Build-Galaxy.ps1 -JavaHome '<JDK 17 경로>' -AndroidSdk '<Android SDK 경로>' -InitializeSigning
```

`-InitializeSigning`은 이 앱의 서명키가 없는 최초 생성 때만 필요하다. 기존 키가 있으면 재사용하며,
키·암호 파일이 일부만 남은 상태는 자동 덮어쓰기 없이 실패한다. 키는 `%LOCALAPPDATA%\Manmool\AndroidSigning\hyeonjang`
안에 Windows 사용자 전용 ACL로 보관하고, 암호 파일은 해당 Windows 사용자에 묶인 DPAPI로 보호한다.
이 파일만 다른 PC로 복사하면 복호화할 수 있다고 가정하면 안 된다. 별도 안전 백업은 사용자 관리 대상이다.

스크립트는 `testDebugUnitTest`, `lintRelease`, `assembleRelease`를 통과한 뒤 로컬에서 서명한다.
개인 키를 Gradle, Git, 공개 산출물에 넣지 않는다. 서명·정렬 검증과 메타데이터가 완성된 고유 폴더만
`dist/1.0.0-<시각>-<고유값>/`로 확정한다. 실패한 `.pending-*` 폴더는 배포본이 아니며 기존 성공본은 보존한다.
`assetlinks.pending.json`은 후속 루트 배포 검토용으로만 생성된다. 이번 작업에서 업로드하지 않는다.

웹 회귀 검사는 저장소 루트에서 `node tests/run-all.js`, Android 소스 안전·변이 검사는
`node tests/galaxy-android.check.js --mutations`로 실행한다. 테스트는 실제 현장 자료를 사용하지 않는다.
메모리 8GB PC에서는 Android 빌드와 웹 전체 회귀를 동시에 실행하지 않고 순서대로 실행한다.
Gradle 작업자는 기본 1개로 제한했다. 최초 의존성 다운로드·변환은 후속 빌드보다 오래 걸릴 수 있다.

### 이번 환경에서의 실패·재시도 기록

- 최신 Android CLI 자동 부트스트랩이 Windows `net.dll` 로드 오류로 실패해, 공식 command-line tools 19.0과 JDK 17 경로로 SDK 설치를 완료했다. PC 전역 PATH는 변경하지 않았다.
- 최초 Android/웹 동시 실행 중 메모리 여유가 부족해 이 작업에서 실행한 Gradle 데몬만 중단했다. 해당 빌드는 실패 이력으로 유지하고, 후속 검사는 순차 진행했다.
- 최초 웹 전체 결과는 **143개 중 141개 통과, 2개 실패**다. 병렬 부하 관련 3개 검사는 러너의 단독 재시도로 통과했다. 사용 브라우저는 시스템 Chrome 152였다.
- `site-rules.e2e.js`, `video-files.e2e.js`는 Playwright 번들 headless Chromium 151로 바꾸어, **앱/기존 검사 코드를 수정하지 않고 2/2 통과**했다. 두 환경의 결과를 혼합해 전체 통과라고 표시하지 않는다. 최초 영상 실패는 합성 시험 영상이 0바이트인 입력 생성 단계였다.
- Android 첫 lint 검사에서 존재하지 않는 helper activity 제거 선언과 API 27 전용 스타일을 API 24 공용 리소스에 넣은 오류가 확인됐다. 불필요 선언을 제거하고 스타일을 `values-v27`로 분리했다. 대신 병합된 release manifest의 activity/provider/receiver/service 허용 목록 검사를 빌드에 추가했다. lint 기준은 낮추지 않았다.
- 다음 증분 빌드에서 생성 폴더의 `ReadOnly` 속성 때문에 `mergeDebugResources`가 `AccessDeniedException`으로 실패했다. 정확히 이 작업의 `android-galaxy/app/build` 경로와 재분석 지점 부재를 확인한 뒤, 생성 산출물 519개에서 읽기 전용 속성만 해제했다. 소스·원본 파일 삭제나 보안 프로그램 설정 변경은 하지 않았다.
- 최종 전체 재검사와 APK 결과는 위 증거 기록란에 별도로 기록했다. 전체 검사 제한 180초 및 기존 업무 검사의 단언은 변경하지 않았다.

Windows에서 웹 검사를 재현할 때에는 동일한 Playwright 번들 브라우저를 명시한다.
시스템 Chrome과 일부 테스트가 사용하는 번들 Chromium이 혼재하지 않도록 실행 환경을 확인한다.

```powershell
$env:NODE_PATH='<Codex Node 의존성 경로>'
$env:PLAYWRIGHT_EXECUTABLE='<Playwright chromium_headless_shell의 chrome-headless-shell.exe>'
$env:HJ_TEST_JOBS='2'
node tests/run-all.js
```

간단한 사용자 설치 안내는 `android-galaxy/INSTALL.ko.md`에 있다.
