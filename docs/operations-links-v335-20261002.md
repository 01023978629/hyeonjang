# v335 운영 연결·동호수 업무·배정 수락 검토

## 요약

사용자가 조사 제안의 1→2→3 진행 및 배포를 승인했다. 기준은 공개 v334, main `6710e52`이다. 이번 변경은 현장 앱/직원 작업실 정적 웹과 별도 직원 서버 **소스**이며 실제 Apps Script 설치·속성·계정·회사/사진/Drive 자료를 변경하지 않는다. 관리사무소 접수는 기존 연결 상태를 한 화면에서 확인하고 기존 검토 화면으로 이어 준다. 새 접수 서버를 임의로 설치하지 않는다.

## 구현

1. 대시보드와 웹 문의에서 운영 연결 점검: 초기 읽기 전용, 직접 눌러 health, 주소 설정/응답/실계정 검증/사진 원본 존재를 구분, 비밀값 비표시, 늦은 응답 폐기.
2. 아파트/등록 동호수·공용부의 안정 UUID 내보내기와 대표의 명시 가져오기. 최초 키는 안전판·CAS·검증된 기기 저장으로 보존. 고객·메모·사진·금액 제외, 같은 서버·목적지 재확인, 자동 동기화/추정 병합/사진 이동 없음. 업무·증빙은 task의 프로젝트/위치를 기준으로 필터링한다.
3. 현재 담당자의 명시 배정 수락. 서버 사용자·시각·버전 기록, 대리 서명/클라이언트 위조 금지, 배정 변경 시 재수락, 진행 보고와 구클라이언트 위치 보존, 응답 유실 동일 UUID, 충돌 시 최신 내용+체크 초기화. 알림은 최신 조회 기준이며 앱을 닫은 동안 푸시/문자는 없다.

## 검사 결과

- 신규 단위/화면/연결 검사는 합성 회사·모의 서버·격리된 브라우저 저장소를 사용한다. 실제 계정이나 원본 사진은 쓰지 않는다.
- 초기 화면 검사에서 테스트가 대표의 빈 '내 업무'에서 동료 업무를 찾는 동선 오류를 발견했다. 실제 팀별 작업실로 들어가도록 테스트를 수정했으며 기대값/시간 제한/재시도 정책은 유지했다.
- 신규 단위 11/11, 직원 화면 10/10, 운영 연결 화면 8/8 시나리오 통과. 기존 회사 업무·프로젝트·운영 검토·버전·문법을 포함한 관련 10개 검사 파일 통과(재시도 없음).
- 최종 보호 제거 48/48 탐지: 새 연결·수락·필터 17개 + 기존 회사 권한/이력 9개 + 프로젝트/보험/원본 22개. `unitId` 확장으로 이동한 기존 history-client/reparent 변이 앵커도 갱신했으며 단언은 유지했다.
- 배포 후보 공개 파일 18개를 만들고 HTTP 제공 파일과 정규화 SHA-256 대조했다. 320/360/1280px 첫 화면·운영 점검·직원 로그인 차단은 오류/실서버 쓰기 없이 통과했다. 모바일 터치 44px·가로 넘침 검사를 통과하고 화면 캡처를 직접 확인했다. 별도 모의 회사로 직원 미체크 수락 창·대표 프로젝트 화면도 확인했다.
- 마지막 코드 수정 뒤 인자 없는 `node tests/run-all.js`는 **223/223 통과, 최종 실패 0, 종료 코드 0**이었다(17.5분·동시 3). `office-ops-conversion`은 병렬 첫 실행의 형제 탭 저장 예상값에서 실패한 뒤 기존 정책에 따른 동일 코드 단독 재시도 106.3초로 통과했다. 재시도는 총 1회이며 검사 단언·180초 제한·재시도 정책을 완화하지 않았다. 합성 자료·모의 서버 검사는 실제 계정/기기 인증을 대신하지 않는다.
- main CI와 공개 사이트 최종 확인은 병합 이후 수행하고 해당 PR의 검증 기록에 실행 URL·버전·18개 파일 대조·비공개 경로 404·화면 결과를 남긴다. 이 문서의 로컬 검사 통과를 CI/실서버 활성화 완료로 해석하지 않는다.
- 전체 회귀 도중 독립 검토로 실제 위치 ID `all`/`unassigned`가 필터 별칭과 겹칠 수 있음을 발견했다. 실행을 중단하고 별칭을 실제 ID에서 허용하지 않는 값으로 분리했다. 해당 ID 위치 두 곳·미지정 업무의 사진이 각각 1장씩 보이는 검사를 추가했다. 마지막 변경 후 전체 게이트를 처음부터 다시 수행한다.
- 다음 전체 검사에서 `mobile-office-connect`가 기존 접수 패널의 첫-child 계약을 위반함을 탐지했다. 새 점검 버튼을 접수 패널 **뒤**로 옮겨 기존 상태 표시 우선순위를 복구했다. 기존 단언·180초 제한·재시도 횟수는 바꾸지 않는다. `office-ops-conversion`의 병렬 첫 실행은 정상 형제 탭 저장 예상값에서 실패했으나 단독 재시도는 통과했다. 해당 보호를 완화하지 않고 후속 단독 검사와 마지막 변경 후 전체 재검사를 수행한다.
- 중간 전체 실행은 222/223(접수 패널 회귀 1건)로 배포를 차단했다. 순서 복구 후 `mobile-office-connect`·`office-ops-conversion`·`operations-connections` 3/3이 재시도 없이 통과했다. 같은 최종 코드로 인자 없는 전체 게이트를 다시 수행한다.

## 재현과 남은 운영 조건

- P0/P1: 최종 검사에서 확인된 결함이 남으면 병합·배포를 중단한다.
- P2/운영 미검증: 실제 별도 Apps Script 서버 갱신, 대표·팀장·직원·외주 실계정 권한 확인, 실제 2기기 변경 수신, Drive 원본 업로드, 갤럭시/아이폰 조작은 별도 승인/사용자 기기가 필요하다.
- 재현: capability 없는 v3 서버에 연결하면 기존 업무 수정은 가능하나 동호수 연결/수락은 업데이트 필요로 표시된다. 실제 서버 배포 없이 이를 활성화 완료로 보고하지 않는다.
- 기존 대표 앱 공용 키 접근은 직원 화면을 추가해도 차단되지 않는다. 대표/직원 운영 전환은 별도 키 교체·백업·접속 계획이 필요하다.
- 동호수 JSON은 사내 대표 전용이다. 이름이나 공개 사례 페이지로 주민·호수·비밀정보를 자동 보내지 않는다.
- 보험 자료 지문은 업무 수락 기록 추가로도 바뀔 수 있다. 제출 전 최신 자료를 다시 검토해야 하며 실제 보험사 전송은 없다.

## 배포 범위와 복구

브랜치 업로드 → PR 검토 → main 병합 → 전체 CI → GitHub Pages → 공개 버전/파일/화면 검증 순서다. 직원 서버 코드는 Pages 허용목록 밖이며 직원 자료/세션/서버 설정을 SW 캐시하지 않는다. 정적 웹 복구는 이 PR을 되돌린 후 같은 검사·Pages 경로로 한다. 실제 사업 자료의 삭제/복원이나 서버 초기화는 복구 절차에 포함하지 않는다.
