# v339 선택 파일 업로드 — 기기 보관과 회사 서버 저장

## 범위와 현재 상태

2026-10-05 사용자 확인: 서류·견적서·정산서는 폴더 스캔 대신 파일을 직접 업로드한다.
고른 원본은 현재 기기에 보관하고 항목·프로젝트로 정리하며 회사 서버에도 저장한다.
기준은 main `f236d39`(v338), 개발 브랜치는 `codex/document-upload-flow-20261005`다.
v339 개발·최종 로컬 검증과 9개 파일 범위를 안내한 뒤 2026-10-05 사용자가 "배포 진행"으로
브랜치 업로드·PR 검증·main 병합·GitHub Pages 공개 배포를 승인했다. 실제 고객 서류는 업로드하지 않는다.

현장 앱 운영 스킬의 원본·금액 보존 원칙을 적용한다. 실제 PC 폴더/원본 이동,
Drive 하위 폴더 이동, 계정, Apps Script 코드/설정/배포, 고객 발송, PC 종료는 변경하지 않는다.

## 사용 흐름

1. 서류함의 **서류 업로드** 또는 견적·정산 화면의 **견적서/정산서 업로드**를 누른다.
2. 파일을 고른 뒤 체크로 필요한 원본만 남기고 서류 항목·프로젝트를 지정한다.
3. **연결된 회사 서버에도 원본 저장**은 기본 미선택이다. 저장 범위·공유 대상을 확인하고 선택한다.
4. **선택 파일 업로드**를 누르면 원본을 기기에 먼저 보관한다. 서버 선택 시 원본 전송과 검증을 이어서 한다.
5. 기기 등록 기록, 서버 원본 확인, 앱 전체 분류 공유 결과를 구분해 표시한다.
   연결 끊김은 목록의 **서버 저장·확인**에서 사용자가 직접 다시 확인한다.

항목/프로젝트 이동은 앱 내 분류만 바꾼다. 파일 이름·PC 원본 폴더·서버 원본 ID는 바꾸지 않는다.
정산서 추가는 매출·견적·수금 합계를 바꾸지 않는다. 금액 읽기는 선택한 PDF/엑셀 견적의 별도 동작이다.

## 저장 범위와 제한

- 기기 보관: 브라우저 IndexedDB의 원본 File. 50개 이내, 파일당 25MiB, 합계 100MiB.
  브라우저 사이트 데이터를 지우면 사라질 수 있으므로 PC 원본도 보존해야 한다.
- 서버 원본: 기존 doc API의 PDF/XLSX/XLS/JPG/PNG, 파일당 9MiB 이내.
  HWP/Word 등 다른 형식·큰 파일은 기기 보관만 완료하며 서버 성공으로 표시하지 않는다.
- 서버 실제 폴더: 기존 공통 doc 폴더(서버 기본 이름 `견적서`).
  `hjdoc_<UUID>.<ext>`의 짧은 전송명으로 저장하고 실제 원본 이름·분류는 앱에서 유지한다.
- 선택 파일의 원본 bytes만 전송한다. 분류 공유를 위한 기존 revision `save`는
  **현재 앱 전체의 프로젝트·고객·견적·정산·수금·파일 분류 정보**를 저장한다.
  두 업로드 확인 화면에서 전체 분류 범위를 별도로 알린다.
- 같은 회사 서버 인증을 가진 사용자는 원본에 접근할 수 있다. 개인별 문서 권한은 아니다.
  통장·계약서 등 민감한 문서를 올리기 전 연결 회사와 공유 대상을 확인해야 한다.
- 다른 기기는 서버 원본의 ID/이름/MIME/크기/SHA-256을 확인한 뒤 원본을 열고 기기에 보관한다.
  원본 확인 전에는 해당 기기에 캐시가 존재한다고 단정하지 않는다.

## 내구성과 중복 방지

기기 등록은 기존 strict readback·안전판·CAS를 유지한다. 서버는 멱등 업로드가 아니므로
legacy relayQueue/자동 재전송을 사용하지 않는다. 고정 연결과 origin Web Lock으로 경합을 막고,
IDB 전송 의도·attempted 예약을 네트워크보다 먼저 저장한다. 응답 ID와 검증 영수증은 앱 CAS보다 먼저 보존한다.
기존 ID·원본 해시·크기·MIME·전송 이름을 바꾸거나 지우는 영수증 갱신을 거부한다.

응답 유실 때는 유일한 UUID명/형식/크기 후보를 다운로드해 전체 원본 SHA-256을 비교한다.
목록 누락/중복/잘림은 ‘없으니 다시 업로드’의 근거가 아니다. 결과가 불명확하면 수동 확인 상태로 남긴다.
기기 캐시의 같은 크기 내용 손상도 해시로 차단한다. 자동 덮어쓰기·원본 삭제는 없다.

전체 안전판 복원은 실제 Drive ID를 유지한다. 같은 원본/연결의 IDB 증빙을 사용해 재검증하고
명시적 서버 확인에서 앱 증빙만 복구한다. 읽기 함수는 원본 캐시·IDB 영수증만 저장하므로
첫 내려받기와 첫 견적 읽기의 객체 신원/시작 fingerprint를 바꾸지 않는다.
