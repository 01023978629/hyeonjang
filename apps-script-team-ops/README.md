# 회사 팀 업무 서버 — v335 소스

`health.service = company-team-v3` 계약을 유지한다. v335는 `project-units-v1` / `task-ack-v1` capability를 health와 권한별 list에 추가한다. capability 없는 v3 서버에서는 기존 업무 수정만 가능하며 새 기능은 잠긴다. 실제 서버의 설치·계정 인증·운영 활성화는 별도 검증 대상이다. 10명 업무 배정·프로젝트 사진·보험 제출 준비의 운영 경계와 제한은 `../TEAM-PROJECT-CLAIMS-v330.md`를 따른다.

`task.history`는 서버가 실제 변경에만 추가하는 업무 보고 기록이다. 작성자·시각·revision은 서버에서 부여하며 클라이언트 history 제출은 거부한다. 업무당 100건, 저장본 전체 4M 문자 제한에 도달하면 기존 자료를 보존하고 중단한다. 동일 내용 저장·동일 requestId 재시도는 보고를 중복 추가하지 않는다. legacy 첫 변경은 마지막 보고 baseline만 보존한다. 재배정받은 직원도 과거 보고를 볼 수 있으므로 연락처·출입 암호를 적지 않도록 안내한다. 상세 화면/운영 경계는 `../TEAM-WORKSPACES-v329.md`.

이 디렉터리는 **별도 Apps Script 프로젝트**용입니다. 기존 사진 릴레이 또는 관리사무소 포털에 `doPost`를 덮어쓰지 마세요. Pages 산출물에서 제외됩니다. 실제 서버 배포·속성 설정·직원 연결은 아직 하지 않았습니다.

## 사용 흐름

1. 대표가 회사 직원용 포털 계정을 관리합니다. 팀 화면은 기존 `portalLogin`/`portalMe`를 신원 확인에만 사용합니다.
2. 별도 회사 서버에 포털 `userId`+`officeId`를 회사 직원으로 연결합니다. 관리사무소 역할만으로 회사 권한이 생기지 않습니다.
3. 대표가 팀·팀장·직원·외주를 구성하고 현장명/업무/담당자/기한을 배정합니다.
4. 직원은 본인 업무의 진행·막힘·인수인계를 기록하고 검수를 요청합니다. 대표 또는 해당 팀장이 완료를 승인합니다.
5. 다른 기기는 ‘최신 자료 확인’으로 확인합니다. 자동 푸시·오프라인 저장·백그라운드 동기화는 없습니다.

기본 팀은 대표·관리, 누수·배관팀, 인테리어팀, 관리사무소 대응팀입니다(사용자 확인 완료). 부트스트랩은 대표 한 명만 연결합니다. 나머지 실제 직원 이름·계정·소속은 임의로 만들지 않습니다.

| 회사 역할 | 업무 보기 | 배정·검수 | 조직·권한 변경 |
| --- | --- | --- | --- |
| 대표·관리자(owner) | 전체 | 전체 | 가능 |
| 팀장(lead) | 소속 팀 | 소속 팀 | 불가 |
| 직원(member)·외주(external) | 본인 배정 | 본인 진행/인수인계만 | 불가 |

퇴사/비활성화 전 남은 업무를 재배정해야 합니다. 자기 관리자 권한 해제 및 마지막 관리자 제거는 차단합니다. API는 상태·역할·팀 범위를 다시 확인하며 숨겨진 버튼에 의존하지 않습니다.

## 활성화 전 필수 확인

- **회사만 통제하는 전용 신원 단지**를 사용해야 합니다. 고객 아파트 관리소장이 비밀번호를 재발급할 수 있는 단지를 회사 직원 신원으로 쓰지 마세요. 포털 관리자는 사실상 회사 로그인 신원을 관리합니다.
- 기존 대표용 `index.html`과 공용 `APP_TOKEN`은 여전히 회사 전체 자료에 접근할 수 있습니다. 직원 페이지 추가만으로 과거에 배포한 공용 키가 무효화되지 않습니다. 직원이 이미 공용 키를 안다면 별도 승인·백업·기기 전환 계획에 따라 키를 교체하고 대표 앱을 분리해야 합니다. 이 작업은 자동 실행하지 않습니다.
- (v333) 보험 준비 건의 단계 충족 점검 `teamClaimReadiness_` — 선택한 증빙에 작업 전·원인 확인·마무리 사진 각 1장, 서류 PDF 1개가 있는지 본다. **경고만 한다**(`claims[].readiness`·`claimBundle.readiness`·검토 기록 `review.warnings`). 필수 서류는 대표가 정하기 전이라 `claimReview`는 여전히 `claim-incomplete` 규칙으로만 막는다. 목록에 `reviewedAt`·`reviewStale`(검토 뒤 자료가 바뀜)을 함께 준다. 서버 소스만 바뀌었다 — 반영은 대표가 손으로 배포한다.
- 직원 화면은 기존 IndexedDB, 원본 사진, 견적, 연락처, 회사 공용 연결정보를 자동 이관하지 않습니다. 새 회사 서버에는 명시 등록한 업무·권한·프로젝트 사진·대표 전용 보험 준비 자료를 저장합니다. 업무 본문에 고객 출입 암호/연락처를 입력하지 마세요.
- 실제 대표·직원·다른 팀·퇴사 계정으로 인증, 접근 차단, 2기기 충돌/재시도 검증이 필요합니다. 모의 검사 통과는 실계정 인증 성공이 아닙니다.
- 독립 프로젝트 배포와 Drive 폴더 생성/속성 설정은 외부 변경입니다. 대상과 범위를 승인받은 뒤 수행하세요.

## 승인 후 서버 설치 절차

1. 새 Apps Script 프로젝트에 `Code.gs`, `TeamPure.gs`, `TeamProjects.gs`, `TeamEvidence.gs`, `TeamMedia.gs`(v333), `appsscript.json`을 설치합니다. 배포자 전용 비공개 Drive 폴더를 마련합니다. 공개 공유뿐 아니라 다른 편집자·뷰어가 있는 폴더도 사용하지 않습니다. 공유 상태이면 코드가 접근을 중단하며 공유 해제를 자동 실행하지 않습니다.
2. Script Properties를 아래와 같이 설정합니다. 실제 값은 Git/보고서/콘솔에 기록하지 않습니다.

   | 속성 | 값 |
   | --- | --- |
   | `COMPANY_ENABLED` | `1` |
   | `COMPANY_PORTAL_URL` | 회사 직원 포털의 고정 `/exec` URL |
   | `COMPANY_FOLDER_ID` | 새 전용 비공개 Drive 폴더 ID |
   | `COMPANY_OFFICE_ID` | 회사가 통제하는 전용 신원 단지 ID(로그인 코드와 다름) |
   | `COMPANY_OWNER_USER_ID` | 검증된 대표 포털 userId |
   | `COMPANY_OWNER_NAME` | 대표 표시 이름 |

3. 프로젝트 소유자가 편집기에서 `companyBootstrapFromProperties_()`를 한 번 실행합니다. 기존 `COMPANY_HEAD`가 있으면 중단하며 덮어쓰지 않습니다. 임시 대표 속성 두 개는 성공 후 제거됩니다. 비밀번호를 생성하지 않습니다.
4. 배포자 권한으로 실행되는 웹 앱을 배포합니다. 클라이언트가 호출 가능한 접근 범위라도 모든 실제 자료 요청은 서버에서 인증·구성원 권한을 재확인합니다. 도메인 정책에 따라 허용되지 않으면 이를 우회하지 마세요.
5. 직원 작업실 로그인 칸 아래 「서버 연결 설정」에 **이 새 회사 서버**의 `/exec` URL 을 넣고 [연결 확인 후 저장]합니다(v333 — health 가 `company-team-v3` 일 때만 이 기기에 저장, 비밀값 아님). 모든 기기에 고정하려면 `team-config.js`의 `apiUrl`에 같은 URL 을 넣어 배포하며, 그러면 고정 주소가 기기 입력보다 우선합니다. `APP_TOKEN`·비밀번호·세션 토큰은 절대 넣지 않습니다.
6. 직원들이 로그인 후 표시되는 식별정보를 회사 관리자에게 전달하면 관리자가 ‘직원 권한 연결’에서 등록합니다.
7. 대표 계정으로 「권한 점검 → 전 직원 권한 점검」을 누르고, 팀장·직원·외주 계정으로 각각 「내 권한 확인」을 눌러 모두 ✓ 인지 봅니다. 그 뒤 2기기 실제 검사를 통과하면 Pages와 운영 활성화를 각각 확인합니다. 클릭 단위 순서와 점검 결과 읽는 법은 `../docs/team-ops-setup.md`.

## 권한 점검 `companyDiagnose` (v333)

대표(owner)만 호출할 수 있는 **읽기 전용** 액션입니다(다른 역할은 `forbidden`, payload 는 비우거나 `{}`). 저장본·HEAD 를 바꾸지 않습니다.
돌려주는 것: 스크립트 속성의 **있음/없음 불리언**(값은 돌려주지 않음, `COMPANY_OWNER_*` 는 부트스트랩 뒤 `false` 여야 정상), 자료 버전, 팀·업무 수,
구성원마다 실제 게이트(`teamMember_`·`teamPresent_`·`teamCanAssign_`)를 돌린 결과 — 접근 가능 여부, 보이는 업무 수와 업무 ID 목록의 SHA-256 지문,
보이는 팀·배정 가능 팀 ID, 동료 식별정보·감사 이력 노출 여부, 연결 단지 일치 여부. 포털 userId·officeId·폴더 ID·URL 은 돌려주지 않습니다.
화면은 이 결과를 화면 쪽에 따로 적은 역할 규칙(대표 전체 / 팀장 자기 팀 / 직원·외주 자기 배정)과 맞춰 ✓·✗ 로 보여 줍니다. 옛 서버는 `invalid-action` 이며 화면은 재배포를 안내합니다. 서비스 이름(`company-team-v3`)은 그대로라 옛 서버에서도 로그인은 됩니다.

## v333 사진·동영상 올리기(HEIC·동영상·실패 후 재시도)

- HEIC/HEIF 사진은 **원본 그대로**(12MiB 이하) 저장한다. 서버는 `ftyp`+HEIF 브랜드로 형식을 확인하고, JPEG 변환은 직원 화면의 미리보기에서만 한다. 원본 보존 계약(편집·압축·변환 없음)과 보험 증빙 원본 요구 때문이다.
- 동영상(MP4·MOV·WebM, 최대 100MB, `TEAM_VIDEO_MAX`)은 `evidenceMediaBegin` → `evidenceMediaChunk`(1MiB, 256KiB 정렬) → `evidenceUpload{uploadId}` 순서다. Drive 파일 ID를 먼저 받아 Script Properties `TEAM_MEDIA_JOB_<uploadId>`에 적은 뒤 바이트를 보낸다 — 응답이 끊겨 다시 보내도 원본은 하나다. 진행 위치는 서버(Drive)가 정본이고, 다시 보낸 청크는 붙이지 않는다. 청크마다 권한을 다시 확인한다. 완성 확인은 Drive의 SHA-256(`sha256Checksum`)·크기·형식·부모 폴더로 한다(100MB를 Apps Script 메모리에 올리지 않는다). 재생·보험 묶음은 `evidenceReadChunk`(1MiB)로 읽고 화면이 전체 SHA-256을 다시 맞춘다.
- 업로드 진행은 회사 스냅샷을 만들지 않는다(청크 100개가 revision 100개가 되지 않게). 작업 기록은 진행 중 최대 100건, 증빙이 확정됐거나 7일(Drive 이어 올리기 세션 수명)이 지난 것만 지운다. Drive 원본은 자동 삭제하지 않는다.
- 동영상은 보험 묶음 50MiB 상한 계산에 그대로 들어간다. 큰 동영상은 묶음에서 빼고 [원본 동영상 받기]로 따로 전달한다.
- `script.external_request` 와 `drive` 범위는 이미 매니페스트에 있다. 배포 후 재승인 화면이 나오면 대표가 승인한다.
- 구서버(이 파일이 없는 v3)에 새 화면이 붙으면 동영상은 `invalid-action`, HEIC는 `invalid-file` 로 대기열에 '실패'로 남는다 — 서버를 갱신한 뒤 [다시 올리기]를 누르면 된다.

## v335 아파트 연결·업무 수락 (실제 서버 갱신은 별도 승인)

- 대표 앱의 「운영 연결 점검 → 연결 JSON 만들기」에서 이름·등록 위치·UUID만 내보낸다. 직원 작업실 대표가 프로젝트 등록/수정에서 같은 서버 JSON을 붙여 넣고, 미리보기의 원본 아파트와 대상 아파트를 비교한 뒤 확인·저장한다. 이름으로 추정하거나 원본 사진·예전 업무를 자동 이동하지 않는다.
- `projectSave`의 선택 필드 `sourceKey`는 UUID v4, 회사 내 유일하며 연결 후 불변이다. `units`는 최대 500곳, `{id,type,dong,ho,name}`만 허용한다. 동·호수는 양의 정수 문자열, 공용부는 40자 이내 이름이다. 중복 ID/표시는 거절한다. 업무가 참조하는 위치는 변경/제거하지 못한다.
- `taskSave` / `taskBatch`의 선택 `unitId`는 해당 프로젝트의 등록 위치여야 한다. 직원은 배정 위치를 바꿀 수 없다. 원본 증빙이 연결된 업무는 프로젝트/위치를 바꿀 수 없다. 구클라이언트가 `unitId`를 생략한 진행 보고는 기존 위치를 보존한다.
- owner는 전체 위치와 연결 키를 본다. 그 외 역할은 자신이 볼 수 있는 업무의 위치만 받으며 연결 키는 받지 않는다. 팀장은 아직 자기 팀 업무에 쓰이지 않은 새 위치를 선택할 수 없으므로 대표가 먼저 배정한다.
- `taskAcknowledge`는 현재 담당자만 `{id,assignmentVersion}`를 보내며 실제 server 시간·사용자·배정 버전으로 영수 기록을 쌓는다. 관리자도 동료 대신 서명하지 못한다. 변경된 배정에 이전 확인을 사용할 수 없고 충돌 후 화면은 최신 내용을 보여 주며 체크를 다시 요구한다. 같은 요청 UUID는 기존 결과를 돌려준다. 같은 배정 버전을 다시 확인해도 수락 기록은 중복되지 않는다.
- 위치·담당자·현장·일정·관리자의 지시가 바뀌면 배정 버전을 올리고, 작업자의 진행 보고는 유지한다. 수락은 작업 시작/완료 승인과 별개다. 최대 100건 수락 기록에서 중단하며 예전 기록을 지우지 않는다.
- 프로젝트·업무 내용 변경은 보험 준비 자료의 지문에도 영향을 준다. 수락 기록 추가도 자료 버전을 바꾸므로 보험 제출 전에 기존 방식으로 다시 검토한다. 자동 보험 제출/문자/카톡/푸시는 없다.

## 보존·충돌·용량

- 매 변경마다 불변 JSON 스냅샷을 만들고 읽기 검증 후 작은 `COMPANY_HEAD` 포인터만 갱신합니다. 이전 스냅샷·실패 잔여 파일을 자동 삭제하지 않습니다. 복구가 필요하면 관리자 검토 및 별도 승인이 필요합니다.
- 자료는 최초 인증 발급 서버/단지에 묶입니다. 속성만 다른 인증 서버로 바꾸면 `configuration-mismatch`로 중단됩니다. 별도 검증된 이관 없이는 변경하지 마세요.
- revision이 다르면 사용자 초안을 보존하고 비교를 요구합니다. UUID 요청 ID가 같으면 중복 실행하지 않으며 같은 ID로 다른 내용을 보내면 거부합니다.
- 세션은 브라우저 메모리에만 보관합니다. 서버는 매 요청의 `portalMe`를 확인합니다. 캐시는 인증 결과를 저장하지 않고, 1분 전역 300회/해시 슬롯 60회의 best-effort 요청 제한에만 씁니다. Apps Script/CacheService의 공유 할당량 및 캐시 퇴거 특성 때문에 전문 방화벽이나 강력한 DoS 방어를 대신하지 않습니다.
- 한 저장소 상한: 팀 50, 직원 100, 업무 2,000, 변경 요청 10,000, JSON 문자열 4,000,000자. 한도 도달 시 기존 기록을 지우지 않고 중단합니다. Drive 스냅샷이 계속 증가하므로 보관 정책과 관찰이 필요합니다.
- 감사 이력은 변경자/대상/시간/버전이며 화면에는 최근 100건을 보여 줍니다. 변경 내용 전문은 과거 비공개 스냅샷에 보존됩니다. 인증된 대표가 기록을 관리하는 구조로, 별도의 변조 불가능한 외부 감사 시스템은 아닙니다.

## 기존 두 업무판의 전환

기존 로컬 팀 업무와 공용 서버 할일에서 `company-task-drafts-v1` JSON 초안을 내려받고, 직원 페이지에서 한 건씩 내용·팀·담당자를 검토해 새 서버에 등록합니다. 같은 `sourceRef` 중복 등록은 차단합니다.

**자동 양방향 동기화나 기존 업무 삭제는 하지 않습니다.** 이후 새 회사 업무를 정본으로 사용하려면 관리자가 전환 범위와 날짜를 정하고 구성원에게 안내해야 합니다. 사진/견적 전체 프로젝트와 자동 연결하거나 기존 완료 표시까지 함께 변경하는 기능은 이번 범위에 포함되지 않습니다. 미확정 업무를 추정하여 옮기지 않습니다.
